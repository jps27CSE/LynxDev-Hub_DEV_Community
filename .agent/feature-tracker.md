## Known Debt

- ~~`npm run format:check` fails on 45 files repo-wide~~ — **resolved.** `npx prettier --write .` applied across 53 files as its own commit; `format:check` now exits 0. Verified by building `HEAD` and the formatted tree separately and diffing the prerendered HTML — all 5 blog posts render byte-identical, so the 13 removed `{" "}` markers were provably redundant rather than assumed to be. Full record in `docs/engineering-gap-report.md` §11. **Now enforced**: CI #31 ran `format:check` on `development-branch` at `3462517` and the job passed, which is the observation this entry was written to wait for. Note the difference from "the trigger covers the branch" — the trigger existing is a claim, a passing run is evidence.
- The main app sidebar (`app/(routes)/_components/Sidebar.tsx:20-26`) has no Admin link, so `/admin` is reachable only by typing the URL.
- `db.execute()` returns a `[rows, fields]` tuple on this stack, not rows. Use the Drizzle query builder (`db.select().from(...)`) as every other `lib/*` file does — a raw-SQL helper that treats the result as rows reads the field-metadata array instead.
- The site notice renders only after hydration, not in SSR HTML — the dismissal check reads `sessionStorage` in an effect, so SSR must render `null`. Accepted: every interactive page on this app needs JS anyway. See plan §16.2 for the no-flash upgrade path if a no-JS route ever needs it.
- A cache TTL set inside a layout becomes that route's ISR window, not just a cache lifetime. `unstable_cache({ revalidate })` propagates to the enclosing route. Measured: a 60s notice TTL turned 4 fully static routes into per-minute revalidation, ~26% of the Vercel Hobby function budget. Always diff the `npm run build` route table when adding a layout-level cache. See plan §16.1.
- A category reaches a question **only** through `interview_question_chapters` — `interview_questions` has no `category_id`, so a question with no chapter link is invisible in every UI (counts, tag filters, practice) while still occupying a row. As of the v1.1.0 rebuild, **130 of 1,078 questions (12%) are linked to no chapter**; only 948 are reachable. So the "1,000+" figure in marketing copy is the *bank* size, not the browsable size, and the two numbers must not be used interchangeably. Verify reachability with `SELECT COUNT(DISTINCT question_id) FROM interview_question_chapters` before quoting a headline number, and link or retire the orphans before claiming any count is fully browsable.
- Any new `fixed top-*` overlay must be checked against every other `fixed` element, not just its own z-index. The site notice banner at `z-40` covered the `z-30` mobile sidebar toggle because they occupied the same 12px origin — it made phone navigation impossible. Overlap in space, not just stacking order, is the failure mode. See plan §17.1.
- The §17.1 fix for that was `top-16 lg:top-0`, justified as *"returns to `top-0` on desktop where nothing is in the way"*. That was audited against `AppShell` only, and it is **false**: the banner mounts in the **root layout**, so it renders on every page, while the public `Header` is `sticky top-0 z-50` at **every** breakpoint. So `lg:top-0` put the banner under the header on `/` and `/blog/*` — losing on stacking order (`z-40` < `z-50`) and showing only as a ghost through the header's `bg-[#05060a]/80 backdrop-blur-xl`. **Lesson: a global overlay's correct offset is route-dependent, so auditing it inside one route group is not an audit at all — enumerate every route group that mounts different top chrome.** Fixed by measuring instead of hardcoding: `useTopChromeOffset` in `components/SiteNoticeBanner.tsx` takes `max(getBoundingClientRect().bottom)` over `header[data-site-header]` and `button[aria-label="Toggle sidebar"]`, skipping zero-height (i.e. `display:none`) elements so a breakpoint-crossing chrome contributes nothing. Verified in real Chrome: `/` and `/blog` clear the 65px header by 12–16px, `/sign-in` (no header) stays flush at 0, and the mobile toggle (bottom edge 48px) is cleared by 12px. The old `lg:top-0` measured a **49px overlap**. Generalisable rule: if a value must differ per route, compute it from the DOM — do not encode route knowledge in a breakpoint class.
- `revalidateTag` in Next 16 takes a second argument (`profile`). `updateTag` is the stronger read-your-own-writes primitive but is Server-Action-only, so Route Handlers must use `revalidateTag(tag, { expire: 0 })`. See plan §18.1.
- A `catch` that returns `serverError()` without logging the error leaves a 500 with no diagnosable cause. `withRequestLog` records the status but not the reason. `app/api/admin/site-notice/route.ts` logs via `log.error`; the three older `app/api/admin/*` routes still do not. See plan §19.1.
- `proxy.ts` runs `auth.protect()` on every route outside its public list, so unsigned API calls get a 307 to `/sign-in` before the handler runs. Handler-level `auth()` / `isAdmin()` are defense-in-depth, and the 401 / 403 / 405 they return are unreachable unsigned — do not treat them as the auth boundary. See plan §18.2.
- `npm run typecheck` passing is **not** sufficient verification. Two real defects in the site notice form passed `tsc` and were caught by `npm run build` (mysql2 in the client bundle, plan §21.3) or by running the code (an unparsable expiry silently serialised to `null`, §21.5). Type errors and bundler errors are different error classes; always build, and prefer a scratch script that exercises real behaviour over reasoning about it.
- Reading the current time during render (`Date.now()`) is a hydration mismatch waiting to happen — the server and client evaluate it in different moments. Sample it in an effect and treat `null` as "not yet known", the pattern `SiteNoticeBanner` uses for `sessionStorage`.
- **Asserting a conclusion from a partial sample of the surface is the same error as asserting it from reading.** Scoping the CI change, I checked the one build-time DB call I already knew was guarded — the root layout's `getActiveSiteNotice`, which catches and returns `null` — and generalised from it to "the build does not need a database". Running it with `DATABASE_URL` unset exited 1: `/interview` is statically prerendered and its chapter query throws. One sample out of roughly a dozen prerendered routes, and it was the one that had the guard. Rule: when a claim covers a *set*, name the set and measure all of it, or state the claim as a sample. See gap report §11 (1.1).
- **When adopting a gate, verify its precondition first.** The schema-drift check (I.15) only became safe to add after `drizzle-kit generate` was run on a clean tree and confirmed no drift — `drizzle-kit` has no `--dry-run`, so the answer is not available read-only. Adding a drift gate to a drifted repo makes CI red on day one, which is the §1 "always-red gate" failure restated. Same reason CI was fixed before its trigger flipped: green first, then visible.
- A gate that is already written but never wired up is worse than absent, because it reads as covered. `npm run check:blog-toc` had been sitting in `package.json` guarding a drift class Known Debt explicitly records (hand-maintained anchors render as links that navigate nowhere, and neither `tsc` nor the build catches it). It also reveals its own ordering requirement — it reads prerendered HTML, so it must sit after `Build` or it reports `no prerendered HTML` on all 5 posts. When adopting an existing script as a CI step, run it against a clean tree first: a gate that has never been run is an untested gate. **A gate that is *named* but never written is one step worse.** `config/system-design/registry.ts:10` cites `npm run check:system-design` as verifying the registry in both directions — that script does not exist in `package.json` or `scripts/`, and there are no `modules/` or routes for it to verify. A forward-looking comment describing a checker that does not exist yet reads identically to a checker that runs. Say which one it is.
- **A suite that has never been observed failing is an untested gate.** Green tells you the assertions agree with the code; it cannot tell you the assertions would notice the code changing. Every target in the I.13 harness was deliberately broken and re-run (`Number()`→`parseInt()` 6 failures, dropped `<head>` injection 2, `Object.hasOwn`→truthiness 9) before being trusted. Cheap, and it is the only thing that distinguishes a gate from a green light wired to nothing.
- **Naming an unasserted boundary is not coverage.** The assertion that actually protects a learner in the editor preview is `sandbox="allow-scripts"` on the consuming `<iframe>` (`components/editor/BrowserPreview.tsx:37`, `LessonClient.tsx:307`) — it lives in `.tsx` and cannot be reached from a unit test. `tests/editor.test.ts` states in-file that passing its suite does **not** mean lesson code is contained, rather than letting a green tick imply otherwise. When a boundary cannot be asserted, say so where the reader will see it, not in a report nobody opens.
- An "empty means none" field needs to distinguish *empty* from *unparseable*. A single `null` for both lets a typo silently clear a setting and the save still reports success.
- **An unmeasured risk stated as "unconfirmed" is still unmeasured.** The gap report recorded that `npm audit` had timed out, so whether any of the 55 outdated packages carried a known CVE was *unconfirmed* — and that caveat sat there while the answer was **3 critical and 11 high**, two of them bypassing `proxy.ts`, the file that IS the auth boundary. The tool that closes a gap is sometimes just the one that was never run. Retrying a "flaky" verification before writing it off is cheaper than living with the unknown: the audit call that had timed out took seconds when attempted.
- **A comment asserting a library honours an undocumented option is a claim, not a behaviour.** `config/db.tsx` passed `acquireTimeout` with a note that it was "honored at runtime" despite not being in mysql2's `PoolOptions`. mysql2 logs `Ignoring invalid configuration option... in future versions an error will be thrown` — six times per build. I.5 credited that option for surviving TiDB cold starts and it **was never in effect**. When a comment justifies something by saying a library accepts it, check the library's log output for a warning saying it doesn't.
- **The proxy can shadow a handler's own auth, and a correct handler can still never run.** `/api/cron/cleanup` has correct fail-closed bearer-token auth, and was unreachable: `auth.protect()` 307'd the Vercel cron job to `/sign-in` first, so the nightly cleanup silently never ran while the gap report described the route as "legitimately public." Two files disagreed and nothing surfaced it. Any route with its own auth must ALSO be in `isPublicRoute`, or its handler is dead code — and "I read the handler" is not evidence the handler runs.
- `log.error(err)` looked safe because dev prints the raw object — but production serializes through `lib/logger.ts`, and that serialization was the thing that could leak. It kept only `{name, message, stack}` and dropped `cause`, so Drizzle's bound params (repeated by `ON DUPLICATE KEY UPDATE`, ~4x per write) landed in the log while `code`/`errno`/`sqlState` were lost. Two rules: **always verify a log change in `NODE_ENV=production`**, never trust the dev output, and note that redaction cannot be line-based when a value is legitimately multi-line. See plan §20.
- Page-level `metadata.title` does **not** deep-merge into an `openGraph`/`twitter` object declared in the root layout. The browser `<title>` was correct while `og:title`/`twitter:title` silently fell back to the generic site name — every social share looked like the homepage. Any route needing correct share metadata must declare its **own** `openGraph`/`twitter` block; `lib/blog-seo.ts` centralises this for the blog. Same failure mode as two sources of truth for a title.
- Capping only the **article** width is not enough for a two-column reading layout — the sidebar then gets flung to the viewport edge, leaving a dead gap. Cap the *group* (container), and cap it twice if the sidebar is conditional, so the single-column case does not leave the prose stranded off-centre. Verified by sweeping breakpoints 375→1920px after each change.
- `position: sticky` can only travel within its **parent's box**. In a flex/grid row without `self-stretch`, the cell collapses to content height and the sticky child appears not to stick at all — it just scrolls away. Symptom looks like broken `position`, cause is a zero-height containing block.
- Two responsive variants of the same component must not each run their own scroll-spy: that is two `IntersectionObserver`s doing identical work, one permanently inside `display:none`. Collapse both variants into one component and reposition it with grid `order` rather than duplicating the hook.
- Hand-maintained anchors (blog TOC) drift silently — a renamed `id` renders as a normal link that navigates nowhere, and neither `tsc` nor the build catches it. Worse, a checker that only validates one direction reports "all clear" for a post that was never registered. `npm run check:blog-toc` checks config→HTML *and* HTML→config; keep both directions when adding any manifest-style check. The same script also asserts each `page.tsx`'s `SLUG` against `config.slug`, because a typo'd slug makes `getPost()` miss while the page still renders.
- A plain-string `metadata.title` is a *template input*, not a final value — the root layout's `template: "%s | LynxDEV"` still appends to it, which rendered the blog index as `"Engineering Blog | LynxDEV | LynxDEV"`. Long post titles hid it in casual reading; only the short index title made it visible. Use `{ absolute: ... }` when composing a title yourself. Corollary: a fix review can find the *real* bug only by re-checking the symptom after an earlier fix changed the cause — the assumed 404-title issue dissolved, exposing this one.
- An `unstable_cache`-era post claiming "fixed" must list **which execution surfaces** were audited. The browser-sandbox claim was true for the worker path and false for the iframe path — same feature, two code paths, one silently left open.
